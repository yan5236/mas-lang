# 功能需求：time 预编译原生产物分发

> 本规格用于承接 [specs/005-time-standard-library/design.md](../005-time-standard-library/design.md) 已落地的 “`time` 包自带 C 宿主层 + 通用原生绑定” 方案，进一步解决“调用方机器没有本机 C 编译器时，`stdlib/time` 依赖可能无法构建”的消费侧阻塞问题。本轮范围只做规格设计，不进入实现。

## 需求 1：支持无本机 C 编译器的依赖消费

**用户故事**：作为 Mas lang 应用开发者，我想要在项目里直接依赖 `stdlib/time`，即使我的机器没有安装 `gcc`、`clang` 或 `cl.exe`，也能完成构建，以便把时间能力当成普通标准库依赖使用。

#### 验收标准 (EARS格式)

1. WHEN 应用工程导入 `time` 并且当前目标平台命中受支持的预编译产物矩阵 THEN 系统 SHALL 在不要求调用方机器安装本机 C 编译器的前提下完成原生依赖解析与最终链接。
2. WHEN 链接器读取到 `time` 包同时声明了预编译产物与 C 源文件 THEN 系统 SHALL 默认优先消费与当前目标完全匹配的预编译产物，而不是直接调用源码编译流程。
3. IF 当前目标不存在可用的预编译产物 AND 调用方没有显式开启“维护者源码构建”模式 THEN 系统 SHALL 在进入最终链接前以中文错误终止，并明确提示当前目标三元组、缺失产物路径以及“普通依赖消费不支持自动回退到源码编译”。
4. WHERE 调用方机器未安装任何本机 C 工具链 WHEN 其使用命中预编译矩阵的 `time` 依赖 THEN 系统 SHALL 仍允许 `import time { ... }` 的构建主链路成功通过。

## 需求 2：把预编译产物作为包内容稳定分发

**用户故事**：作为标准库维护者，我想要把 `time` 的原生产物随包一起分发，而不是临时落在构建目录里，以便 `fama install`、本地路径依赖和未来的包发布链路都能稳定复用。

#### 验收标准 (EARS格式)

1. WHEN 团队为 `stdlib/time` 发布或更新原生产物 THEN 系统 SHALL 把预编译对象文件与对应元数据存放在包目录内的稳定路径，而不是放在 `build/`、`target/` 或其他会被依赖安装流程跳过的目录。
2. WHEN `fama install` 把 `time` 复制到 `mod_module/time@<version>` THEN 系统 SHALL 保留预编译对象文件、目标平台元数据和 `settings.toml` 中的声明信息。
3. WHEN 链接器准备消费某个目标平台的预编译产物 THEN 系统 SHALL 校验目标三元组、包版本、ABI 版本和对象文件清单是否完整且一致。
4. IF 预编译元数据缺失、对象文件不存在或校验结果不一致 THEN 系统 SHALL 拒绝链接并输出中文诊断，而不是静默忽略或回退为隐式源码编译。

## 需求 3：区分调用方消费路径与维护者构建路径

**用户故事**：作为标准库维护者，我想要保留基于 C 源文件重新生成预编译产物的能力，但这条路径不应该默认暴露给普通依赖使用者，以便把“需要本机编译器”的成本收敛到维护侧。

#### 验收标准 (EARS格式)

1. WHEN `time` 的 `native/*.c`、头文件或 ABI 相关声明发生变更 THEN 系统 SHALL 提供显式的维护者产物刷新流程，用于重新生成受支持目标的预编译对象文件与元数据。
2. WHEN 维护者执行产物刷新流程 THEN 系统 SHALL 产出可重复放入包目录的稳定文件结构，并更新能够反映源码版本的指纹或摘要字段。
3. IF 普通 `fama build` 或 `fama run` 没有开启维护者源码构建开关 THEN 系统 SHALL 不得因为缺失预编译产物而自动触发 `cc::Build` 或等价的源码编译动作。
4. WHERE 维护者需要为尚未纳入预编译矩阵的新目标试验构建 WHEN 其显式开启维护者源码构建模式 THEN 系统 SHALL 允许使用源码编译链路生成该目标所需的对象文件与元数据。

## 需求 4：保持 `time` 公开 API 与原生 ABI 的稳定性

**用户故事**：作为 `time` 标准库的使用者，我希望“无编译器消费方案”只改变原生链接来源，不改变我已经使用的公开 API 和运行时语义，以便项目可以无感升级。

#### 验收标准 (EARS格式)

1. WHEN 团队引入预编译产物分发 THEN 系统 SHALL 保持 `unix_seconds`、`unix_millis`、`now_utc`、`now_email_date`、`now_http_date`、`monotonic_millis`、`sleep` 这些公开函数名与返回类型不变。
2. WHEN 链接器消费预编译对象文件 THEN 系统 SHALL 继续沿用 `005-time-standard-library` 已定义的统一原生 ABI，而不是为 `time` 单独发明新的调用约定。
3. IF 预编译产物的 ABI 版本与当前编译器期望不匹配 THEN 系统 SHALL 阻止链接，并要求维护者先刷新对应目标的预编译产物。
4. WHERE 后续 `time` 包新增宿主函数但未改变 ABI 总版本 WHEN 维护者更新包内源码与预编译产物 THEN 系统 SHALL 不要求新增 time 专项编译器业务分支。

## 需求 5：提供面向角色的清晰诊断与支持矩阵

**用户故事**：作为应用开发者和标准库维护者，我想要在成功或失败时都能得到清晰提示，知道当前是“普通消费路径”还是“维护者产物刷新路径”，以便快速定位问题。

#### 验收标准 (EARS格式)

1. WHEN 构建通过预编译产物成功链接 `time` THEN 系统 SHALL 在调试日志或等价可观测信息中标明命中的目标三元组与已使用的预编译对象来源。
2. WHEN 构建因缺失预编译产物而失败 THEN 系统 SHALL 输出中文诊断，并区分“调用方应更换到受支持目标或升级依赖”和“维护者应执行产物刷新流程”这两类处理建议。
3. WHEN 团队维护 `time` 的原生产物分发方案 THEN 系统 SHALL 在规格、任务和后续文档中明确列出当前受支持目标矩阵及其预编译产物位置约定。
4. IF 目标平台未纳入支持矩阵 THEN 系统 SHALL 明确报告“不受支持”而不是把错误表现为模糊的 `gcc`、`clang` 或 `cl.exe` 缺失提示。

## 技术约束 (非功能需求)

1. 主线范围：本规格只覆盖 `stdlib/time` 的 C 宿主层分发方式、`maslang` 的原生链接输入选择逻辑，以及与之直接相关的 `fama` 安装/构建路径；不在本轮扩展其他标准库模块。
2. 设计边界：必须继续保留“Mas lang 调用 C 宿主层获取系统时间”的基本方向，不改回 time 专项编译器内建，也不把 `time` 宿主实现整体迁回 Rust `bootstrap.rs`。
3. 消费约束：普通依赖使用者的默认构建路径不得要求本机具备 `gcc`、`clang`、`cl.exe` 或等价 C 编译器。
4. 路径约束：预编译对象文件必须位于包目录内可被 `fama install` 复制的稳定路径，不能放在当前安装逻辑会跳过的 `build/`、`target/`、`mod_module/` 或 `.git/` 目录下。
5. 平台约束：当前主线至少必须覆盖 [linker.rs](../../crates/maslang/src/linker.rs) 中默认目标三元组 `x86_64-pc-windows-msvc`；其他目标采用同一声明格式逐步扩展。
6. ABI 约束：预编译方案只能复用现有统一原生 ABI；任何 ABI 变化都必须体现在版本字段和产物刷新流程中，禁止隐式兼容。
7. 诊断约束：所有面向调用方与维护者的失败提示必须使用中文，并明确指出当前角色、目标平台和下一步操作建议。
8. 发布约束：预编译产物必须可重建、可追溯，至少需要记录与源码/头文件版本相关的指纹信息，避免把过期对象文件误当成最新发布内容。
