# 实施任务清单：time 预编译原生产物分发

## 阶段 1：补齐包级预编译协议

- [x] 1.1 扩展 `stdlib/time/settings.toml` 的 `native` 配置模型，加入 `abi`、`source_fallback`、`prebuilt.<target>` 等字段定义，并明确与现有 `native.sources` 的共存关系 [关联: design.md 2.2, 2.3]
- [x] 1.2 约定 `native/artifacts/<target-triple>/` 目录结构、对象文件命名规则和 `manifest.toml` 字段集合，保证产物不落在 `build/` 或 `target/` 等会被安装流程跳过的目录 [依赖: 1.1] [验证 Req 2]
- [x] 1.3 固化首批支持矩阵，至少覆盖当前默认目标 `x86_64-pc-windows-msvc`，并为后续 POSIX 目标保留相同声明格式 [依赖: 1.2] [验证 Req 1, Req 5]

## 阶段 2：调整链接器的原生输入选择逻辑

- [x] 2.1 把 `crates/maslang/src/linker.rs` 中现有的 `compile_native_objects()` 设计重构为“预编译优先、显式源码回退次之”的统一原生链接输入解析流程 [依赖: 1.1] [验证 Req 1, Req 4]
- [x] 2.2 为链接器补充预编译元数据校验，至少覆盖目标三元组、包版本、ABI 版本、对象文件存在性和源码指纹字段 [依赖: 2.1] [验证 Req 2, Req 4]
- [x] 2.3 为 `CompileOptions`、`fama build`、`fama run` 或等价入口补充“维护者源码构建”显式开关，禁止普通消费路径自动触发源码编译 [依赖: 2.1] [验证 Req 1, Req 3]
- [x] 2.4 统一链接失败诊断，把“缺少预编译产物”“预编译校验失败”“未开启维护者模式”分别映射成明确中文错误 [依赖: 2.2, 2.3] [验证 Req 5]

## 阶段 3：建立维护者产物刷新流程

- [x] 3.1 设计并实现维护者专用的产物刷新入口，使用 `--allow-native-source-build` 根据 `native/*.c` 与头文件生成目标对象文件和 `manifest.toml` [依赖: 1.2, 2.3] [验证 Req 3]
- [x] 3.2 在产物刷新流程中写入稳定的源码摘要/头文件摘要，确保预编译对象可追溯且可被链接器校验 [依赖: 3.1] [验证 Req 2, Req 3]
- [x] 3.3 为 `stdlib/time` 首批支持目标生成并落库预编译对象文件，验证包目录已具备“普通消费无需本机 C 编译器”的最小闭环 [依赖: 3.1, 3.2] [验证 Req 1, Req 2]

## 阶段 4：校准依赖安装与消费链路

- [x] 4.1 为 `fama install` 增加回归验证，确认 `native/artifacts/`、`manifest.toml` 和 `settings.toml` 中的预编译声明会随依赖一起复制到 `mod_module/<name>@<version>` [依赖: 1.2, 3.3] [验证 Req 2]
- [x] 4.2 为 `maslang` 增加端到端验证，覆盖“调用方机器无本机 C 编译器、但命中预编译矩阵时仍可链接通过”的成功场景 [依赖: 2.4, 3.3, 4.1] [验证 Req 1]
- [x] 4.3 增加失败场景验证，覆盖“目标未命中预编译矩阵”“预编译对象缺失”“ABI 版本不匹配”“未开启维护者模式”四类中文诊断 [依赖: 2.4, 3.3] [验证 Req 2, Req 4, Req 5]

## 阶段 5：补充文档与发布约束

- [x] 5.1 在 `time` 包和工具链文档中记录当前支持矩阵、预编译目录协议以及普通调用方与维护者两条路径的差异 [依赖: 4.2, 4.3] [验证 Req 5]
- [x] 5.2 明确后续当 `native/*.c`、头文件或 ABI 变更时必须先刷新预编译产物，再允许发布新版本的发布检查项 [依赖: 3.2, 5.1] [验证 Req 3, Req 4]
- [x] 5.3 在全部验收完成后回写本任务清单状态，并在相关路线图或后续规格中标记“`time` 已支持无本机 C 编译器的预编译消费模式” [依赖: 5.2] [验证 Req 1, Req 5]
